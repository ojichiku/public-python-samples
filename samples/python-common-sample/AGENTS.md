# AGENTS.md

## 1. プロジェクト概要

このプロジェクトでは、Python アプリケーションで共通して利用できる機能群を
**`common` パッケージ**として実装する。

- CLI ツール
- GUI アプリケーション（例: PySide6）
- DB を扱うツール など

で再利用できる**共通基盤ライブラリ**を整備することが目的。

この AGENTS.md は、人間開発者およびコード生成エージェント
（例: ChatGPT / Codex / Copilot 等）が従うべき「全体ルール」を定義する。

個々の共通機能（ログ、設定、パス操作など）の詳細仕様は、  
`specs/` ディレクトリ配下の spec ファイルに記述する。

---

## 2. ディレクトリ構成ルール

### 2.1 src レイアウト

プロジェクトは **src レイアウト** を採用する。

```text
project-root/
  AGENTS.md
  PLANS.md
  pyproject.toml
  src/
    common/
      __init__.py
      # 共通機能のモジュール群（ファイル名は各 spec に従う）
  tests/
    # pytest 用テストコード
  specs/
    # 個々の共通機能の仕様書（specファイル）
    # 例: logging.md, config.md など
```

* 実装コードはすべて `src/` 配下に置く。
* 共通機能は `src/common/` パッケージにまとめる。
* テストコードは `tests/` 配下に配置する。
* 個別機能の仕様は `specs/` 配下の Markdown ファイルに記載する。
* モジュール名・ファイル名・関数名などの詳細は **AGENTS.md ではなく spec ファイル側で定義する。**

---

## 3. Python バージョン・コーディングルール

* 対応 Python バージョン：**3.13 以降**（必要に応じて変更可）

* すべての新規コードに **型ヒント（type hints）を付与することを必須**とする。

* 可能な場合、ファイル冒頭に以下を追加して将来互換性を高める：

  ```python
  from __future__ import annotations
  ```

* 標準ライブラリで実現できるものは標準ライブラリを優先する。

* 外部ライブラリを追加する場合は、該当機能の spec ファイルに採用理由とバージョン条件を明記する。

---

## 4. コメント・docstring のルール

* **コメントは日本語で記述する。**

  * 例：`# この関数は設定ファイルを読み込み、検証してから返す`
* **docstring も原則日本語で記述する。**

  * 外部公開ライブラリとして英語が必要な場面があれば、その spec で方針を上書きしてよい。
* docstring には可能な範囲で以下を含める：

  * その関数／クラスの目的
  * 主な引数・戻り値
  * 想定される例外や注意点

例：

```python
def example_func(x: int) -> int:
    """
    引数 x を2倍にして返す。

    負の値もそのまま2倍にして返す。
    """
    return x * 2
```

## 5. 共通機能の設計・追加ルール

共通機能を追加・修正する際は、以下のルールに従う。

1. **まず spec ファイルを作成・更新する**

   * `specs/` 配下に Markdown 形式で仕様を書く。
   * 1 機能につき 1 ファイルを基本とする。
   * spec には少なくとも以下を含める：

     * 目的・用途
     * 提供する API（モジュール名・クラス名・関数名・引数・戻り値）
     * 代表的な使用例
     * 想定するエラー・制約
     * テストの観点（どのようなケースをテストするか）

2. **spec に沿って `src/common/` 配下に実装を追加・修正する**

   * 共通機能は極力「汎用的」であること。
   * 特定アプリケーション固有のロジックは別パッケージに切り出す。

3. **テストコード（pytest）を `tests/` 配下に追加・更新する**

   * 各機能の spec に書かれたテスト観点をカバーする。
   * 既存テストがすべて成功することを確認する。

---

## 6. テストルール（pytest）

* テストフレームワークは **pytest を使用する。**
* テストは必ず `tests/` ディレクトリ配下に配置する。
* 共通機能を新規追加・変更した場合は、必ず対応するテストを用意する。
* テストコードにも可能な範囲で型ヒントを付与することを推奨する。

---

## 7. specs/ ディレクトリの運用ルール

* 個々の共通機能ごとに Markdown の spec ファイルを作成する。

  * 例：`specs/logging.md`, `specs/config.md`, `specs/paths.md` など。
* spec ファイル名は原則として機能名と揃える。
* 実装や API 仕様を変更する場合は、**必ず関連する spec も更新する。**
* AGENTS.md には「全体ルール」のみ記述し、
  **個別機能の詳細仕様（ログのフォーマット、設定ファイルの形式など）は spec 側で定義する。**

---

## 8. エージェント（コード生成ツール）への指示

コード生成エージェント（ChatGPT / Codex / Copilot 等）は、以下を守ること。

1. **この AGENTS.md に書かれた全体ルールを最優先で守る。**
2. 個別機能に手を加える場合は、必ず対応する spec ファイルの内容を尊重する。
3. 新しい共通機能を追加する場合：

   * まず `specs/` に spec 草案を作成し、
   * その spec に基づいて `src/common/` に実装し、
   * `tests/` に pytest テストを追加する。
4. モジュール名・関数名・クラス名・細かい仕様を AGENTS.md 内で勝手に増やさない。

   * それらは **各 spec ファイル側で定義する。**

## 9. README の運用ルール（追加）

このプロジェクトでは README を以下の方針で管理する。

### 9.1 README の記述言語  
- **README は日本語で記述する。**  
  - 共通機能の仕様・使い方は日本語で統一し、理解しやすさとメンテナンス性を重視する。

### 9.2 README 分割方針  
共通機能が増えていくと単一 README が肥大化するため、以下の方針で分割して管理する。

- プロジェクトルートの `README.md` は **全体概要のみに限定する**  
  - プロジェクト目的
  - ディレクトリ構成
  - 共通機能の種類（簡単な一覧）

- 各機能の詳細な説明は **specs/ 配下の spec ファイル**に記述する  
  - logging → `specs/logging.md`
  - config → `specs/config.md`
  - errors → `specs/errors.md`
  - paths → `specs/paths.md`  
  など

- 必要であれば、`docs/` ディレクトリを設けて追加ドキュメントを配置してよい  
  - 例：利用ガイド、事例、FAQ、設計メモなど  
  - ただし公式仕様は必ず specs/ に置くこと

### 9.3 README に書かないもの  
README は肥大化を防ぐため、次の内容は **README に直接書かない**：

- API の詳細仕様（specs に書く）
- 実装方針のメモ（developer note は docs/ に）
- コーディング規約（AGENTS.md に集約）
- 作業プロセス（PLANS.md に記載済み）
